## 🎯 Мета роботи

Ознайомитися з підходом мікрофреймворків на прикладі **Javalin**.  
Навчитися створювати базовий **REST-сервіс**, налаштовувати маршрути, обробляти запити через об'єкт `Context`, додавати **middleware** та обробники винятків.  
Виконати **порівняння зі Spring MVC / Spring Boot**.

---

## 📖 1. Короткі теоретичні відомості

### Jetty
Використовується як легковажний вбудований вебсервер, на якому базується Javalin.  
Забезпечує швидкий старт застосунку без потреби у важких серверів застосунків.

### Клас Javalin
Основна точка входу для налаштування сервера, маршрутів та плагінів  
(наприклад, JSON-мапера або статичних файлів).

### Об’єкт Context (`ctx`)
Надає доступ до HTTP-запиту та відповіді.  
Використовується для:
- зчитування параметрів (`queryParam`, `pathParam`);
- отримання тіла запиту (`bodyAsClass`);
- відправки відповідей у форматі JSON.

### Middleware
Обробники `app.before()` та `app.after()`, які дозволяють виконувати логіку  
(наприклад, логування) до або після основного обробника маршруту.

### Exception-handling
Механізм `app.exception()`, що дозволяє централізовано перехоплювати помилки  
та повертати клієнту зрозумілі повідомлення і відповідні HTTP-статуси.

## ⚖️ 3. Порівняльна таблиця Spring MVC vs Javalin

| Критерій | Spring MVC / Spring Boot | Javalin |
|--------|---------------------------|---------|
| Архітектура | Повноцінний фреймворк («Heavyweight») | Мікрофреймворк («Lightweight») |
| Конфігурація | Декларативна (анотації, автоконфігурація) | Явна (програмна конфігурація через код) |
| Керування DI | IoC-контейнер (`@Autowired`) | Ручне створення та передача залежностей |
| Маршрутизація | Анотації на класах/методах контролерів | DSL-стиль (`app.get`, `app.post`) |
| Middleware | Фільтри, інтерцептори, AOP | Лямбда-функції `before` / `after` |

## ❓ 4. Відповіді на питання

### 1. Які основні відмінності між Spring MVC і Javalin?

Spring MVC використовує **декларативний підхід**: розробник описує поведінку
за допомогою анотацій, а фреймворк автоматично знаходить компоненти та
будує зв’язки між ними.

Javalin використовує **явний підхід**: кожен маршрут і кожен об’єкт
створюється та реєструється вручну в коді.  
Javalin не потребує IoC-контейнера, оскільки розробник сам керує життєвим
циклом об’єктів.

Це робить програму прозорішою та швидшою при старті, хоча й збільшує
обсяг ручного коду.

---

### 2. Для чого використовується модуль `infrastructure` у Javalin-проєкті?

Модуль `infrastructure` виконує роль **ініціалізатора застосунку**.  
Оскільки Spring-контейнер відсутній, саме тут через клас
`ApplicationInitializer` вручну:

- створюються екземпляри JDBC-репозиторіїв;
- налаштовується база даних;
- виконується SQL-скрипт ініціалізації таблиць.

Це дозволяє модулю `web` отримати готові об’єкти портів
для передачі в контролери.

---

### 3. Яку роль виконує клас `AddBooksDemo`?

Клас `AddBooksDemo` виступає у ролі **клієнта для тестування REST API**.

Він:
- надсилає `POST`-запити на `/api/books` з JSON-тілом для додавання книг;
- виконує `GET`-запити для перевірки їх наявності.

Це дозволяє перевірити коректність серіалізації/десеріалізації об’єктів
та роботу шару збереження даних **без використання браузера**.

## 5. Висновки

**Відмінності:**  
Spring — це велика екосистема, що бере на себе більшість рутинних задач
через анотації.  
Javalin — це бібліотека, яка надає лише базові HTTP-інструменти, залишаючи
логіку застосунку максимально «чистою» від фреймворку.

**Переваги Javalin:**  
- висока швидкість роботи;
- відсутність «магії» анотацій;
- просте налаштування;
- мінімальне споживання пам’яті.

**Обмеження:**  
Відсутність вбудованих механізмів безпеки та складного DI, що ускладнює
підтримку дуже великих проєктів.

**Доречність використання:**  
Javalin доцільно використовувати для мікросервісів, легких API та
високонавантажених сервісів, де важлива швидкість відповіді.  
Spring MVC краще підходить для складних корпоративних (Enterprise) систем
із готовими інтеграціями та стандартизованою архітектурою.

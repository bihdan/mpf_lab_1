# Лабораторна робота №8

## Тема: Персистентність у Spring Boot: JPA, Hibernate, Flyway та сторінка коментарів користувача

---

##  1. Мета роботи
Ознайомитися з принципами роботи з реляційними базами даних у Spring Boot на основі **JPA/Hibernate**.
Навчитися створювати сутності, описувати міжтабличні зв’язки (**One-To-Many, Many-To-One**),
застосовувати **Spring Data Repository** для виконання CRUD-операцій та керувати схемою БД через **Flyway**.
Закріпити трирівневу архітектуру (**core / persistence / web**) шляхом перенесення логіки з JDBC на ORM-реалізацію.

---

##  2. Опис ролі JPA/Hibernate та ORM

**ORM (Object-Relational Mapping)** — це технологія, що дозволяє відображати
об'єкти мови програмування на таблиці реляційної бази даних.

### Роль у проєкті
Використання **JPA/Hibernate** дозволило відмовитися від ручного написання SQL-запитів,
забезпечивши автоматичне генерування запитів на основі Java-сутностей та інтерфейсів репозиторіїв.

### Переваги над JDBC
- Скорочення обсягу коду адаптерів  
- Підтримка транзакційності на рівні анотацій  
- Автоматичне керування зв'язками між таблицями  

---

##  3. Опис сутностей та зв'язків

У модулі **core** було створено доменні моделі, анотовані як JPA-сутності:

### Book
- Поля: `id`, `title`, `author`, `pubYear`
- Зв’язок: `@OneToMany` до коментарів  
- Каскадне видалення: `CascadeType.ALL`  
- Тип завантаження: `FetchType.LAZY`

### User
- Поля: `username`, `password`, `role`
- Зв’язок: `@OneToMany` до коментарів

### Comment
- Зв’язки: `@ManyToOne` до `Book` та `User`
- Поле `author` замінене на об’єктний зв’язок із `User`

##  4. Flyway-міграції та схема БД

Керування структурою БД автоматизовано за допомогою **Flyway**  
Локація скриптів: `classpath:db/migration`

- **V1__schema.sql** — створення таблиць `books` та `comments`
- **V2__update.sql** — додавання таблиці `users` та зовнішнього ключа `user_id`
- **V3__test_data.sql** — наповнення бази початковими даними  
  (користувачі `admin`, `student`, тестові книги)

##  5. Відповіді на теоретичні питання

### 5.1 Навіщо JPA / Hibernate замість JDBC?
ORM вирішує проблему *object-relational impedance mismatch*,
дозволяючи працювати з об'єктами замість рядків таблиць.
JDBC потребує ручної обробки `ResultSet`,
тоді як JPA робить це автоматично.

### 5.2 Роль Flyway та наслідки ручних змін
Flyway гарантує однакову структуру БД у всіх середовищах.
Ручні зміни призводять до розсинхронізації та помилок виконання.

### 5.3 Транзакції та `@Transactional`
Транзакція — це логічна одиниця роботи.
Анотація `@Transactional` гарантує **rollback**
у разі помилки та збереження цілісності даних.

### 5.4 Зв’язки та проблеми (N+1, Lazy, Cascade)
- **N+1** — вирішується через `JOIN FETCH`
- **Lazy Loading** — завантаження даних лише при зверненні
- **Cascade** — автоматичне керування пов’язаними сутностями

##  8. Висновки
Використання **Spring Data JPA** дозволило повністю усунути JDBC-код,
зробивши шар `persistence` чистішим та легшим у підтримці.

**Flyway** забезпечив контроль версій структури БД та спростив розгортання проєкту.

Дотримання архітектурних принципів дозволило змінювати механізм доступу до даних
без впливу на бізнес-логіку модуля **core**.
